# Upload stability report — self-hosted Teldrive v2 fork

> **Status (updated after the fixes):** addressed in this pass — **M1** (the settings option stored
> `conflictPolicy: "error"`, which is not in the API enum, so every `POST /v1/uploads` returned 400;
> fixed to `"fail"` with validation on load so already-poisoned localStorage heals), **C1** (per-part
> retry with exponential backoff + jitter and a 120 s stall watchdog), **C2** (a non-`open` session no
> longer traps the task forever), **C3** (server-side transient RPC retries now back off with jitter
> instead of retrying instantly), **C6** (pause→resume no longer lets a superseded run clobber the new
> run's controller/status), **C7** (`part busy` 409 is now retried). **Not addressed:** C4 (1 h HTTP
> read timeout vs 512 MiB parts), C5 (resume across reload), C8 (process-wide rate limiter), C9
> (unbounded flood-wait) — each needs a config or architecture decision.

Repo under investigation: `src/teldrive-2` (Go backend + Vite/React UI, gotd v0.162.0, gotd/contrib v0.25.0, River/RiverPro jobs, PostgreSQL).
All paths below are relative to the workspace root (`C:\Users\ptfm\Documents\deepseek-harness\default-workspace`).
This was a READ-ONLY investigation: nothing under `src/` was modified.

## 1. Verdict (ranked, with confidence)

The instability is **client-side and lifecycle-driven first, transport-policy second**. Ranked by (likelihood × impact):

1. **The browser uploader has no retry, no stall timeout, and no way to recover a session that is no longer `open`** (confidence: high, verified by reading). `ui/src/features/uploads/store.ts` runs one sequential part loop per file; the first non-2xx/network error fails the entire multi-GB task (`store.ts:459-463`), and `getOrCreateSession` keeps the stale `uploadId` forever, so once a session is `aborted`/`expired` **every Resume fails permanently** (`store.ts:216-229` + `:413`). This alone produces exactly the reported symptoms: uploads that stall or never finish, opaque failures, and small files looking fine while multi-GB files fail (more parts = more chances to hit a single unrecoverable error).
2. **Transport retry policy is wrong in two opposite ways** (confidence: high, verified by reading source + the installed gotd/contrib versions): the custom RPC-error middleware retries `RPC_CALL_FAIL` / `WORKER_BUSY_TOO_LONG_RETRY` / `STORAGE_CHOOSE_VOLUME_FAILED` **10 times with zero delay and no jitter** (`internal/telegramstore/retry.go:34-48`), i.e. it burns every attempt in milliseconds on errors that explicitly ask for a later retry; conversely FLOOD_WAIT is waited out **unbounded** (no `WithMaxWait`/`WithMaxRetries`: `internal/telegramstore/factory.go:88`), so a part can sit silent for an hour holding a renewed lease with no client-visible deadline.
3. **A 1-hour HTTP `ReadTimeout` is combined with a 512 MiB default part size** (confidence: high on the mechanism): Go arms the read deadline once for the whole request *including the body* (`net/http/server.go:1037-1103`), and it is set from `HTTP.ReadTimeout` (`internal/config/config.go:24`, `internal/app/app.go:237-244`) while the default part is 512 MiB (`internal/uploads/service.go:25`, `ui/.../store.ts:65`). Any link below ~1.2 Mbit/s cannot deliver one part within the deadline, so large uploads fail deterministically mid-body.
4. **Resume essentially does not exist** (confidence: high): the UI persists nothing and discards the legacy persisted queue (`store.ts:57-105`), `POST /v1/uploads` always creates a new session (`internal/api/handler_access.go:497-528`), and the only resumable-session query is used by the background job worker and is additionally gated on `conflict_policy = 'replace'` (`db/queries/uploads.sql:64-80`). A reload silently restarts from zero; the abandoned session keeps its Telegram parts for up to 7 days + the 12 h sweep.
5. **Server has no bound on concurrent part uploads and builds a fresh gotd client + connection pool per part** (confidence: medium-high): 8 connections per part by default, up to 16 parts per background job × 2 workers (`internal/jobs/upload_source.go:355-390`, `internal/jobs/runtime.go:142`), plus every UI file. Combined with finding 1 (no client retry) this converts Telegram-side turbulence into failed files.
6. Two further high-value, easily-confirmed defects: the per-run abort/controller race in the UI store (`store.ts:399,460-468`) which can leave the shelf showing "paused" while bytes are flowing and can start duplicate concurrent uploads of the same part, and the settings UI's invalid conflict-policy value `"error"` (`ui/src/routes/_settings.settings.uploads.tsx:64-66`) which makes **every** new upload fail at request validation (the API enum is `fail|replace|rename`, `ui/src/api/schema.ts:1735`).

I could not run the PostgreSQL integration tests or the race detector (no Podman, no cgo/gcc), so none of the SQL state-machine claims below are test-verified — they are read from `db/queries/uploads.sql` and the service code.

## 3. Verified by reading vs. inferred

**Verified by reading code / SQL / module sources (no runtime):**
- The exact retry loop in `retryMiddleware` (no sleep) and the transient-error list; the middleware order built in `PooledAPI` (`factory.go:165-169`: floodwait outermost, retry inner) and the single shared ratelimit instance.
- FLOOD_WAIT / FLOOD_PREMIUM_WAIT are recognised by the installed waiter (`gotd/contrib@v0.25.0/middleware/floodwait/flood.go` `asWait`, default `SimpleWaiter` = infinite retries, unbounded wait per `simple_waiter.go:51-96`) and additionally by gotd's own uploader (`gotd/td@v0.162.0/telegram/uploader/big.go:34`). So "FLOOD_WAIT is ignored" is **false** — it is respected, but unbounded.
- `ReadTimeout` semantics read from the local GOROOT (`sdk/go/src/net/http/server.go:1037-1103`, `:3062-3070`): one deadline for the entire request including the body.
- All state transitions and guards in `db/queries/uploads.sql` (claim requires `state <> 'stored'` + expired/absent lease; store/fail require the lease token; abort/expire/cleanup restricted to terminal states; `MarkUploadCompleting` requires `state='open'`).
- `Complete()` is a single transaction with `FOR UPDATE` on the session (`internal/uploads/service.go:392-528`).
- Cleanup cannot touch live uploads: `ListUploadPartsForCleanupMany` and `DeleteUploadPartsForCleanup` both require the session to be `aborted`/`expired` (`db/queries/uploads.sql:322-350`).
- Deps/versions from `src/teldrive-2/go.mod` (gotd/td v0.162.0, gotd/contrib v0.25.0) and their sources in `C:\Users\ptfm\go\pkg\mod`.
- The UI store logic (retry gap, session reuse, controller handling, persistence) read line by line.

**Inferred only (not reproduced):**
- The runtime effect of the pause/retry race (C6) — single-threaded reasoning about async ordering, not observed in a browser.
- Concurrent session-blob overwrite consequences (M3).
- That the user's actual bottleneck includes the shared rate limiter (C8) — depends on their uplink (if it is below ~10 MiB/s this is not their bottleneck).
- Any SQL-level behaviour under real concurrency: the claim/lease/expire/cleanup interleavings are argued from the queries, not tested (integration tests are excluded by build tag — see §4).
- Telegram-side behaviour (flood-wait sizes, connection resets) — no live credentials used (`telegramlive` tag not run).

## 5. Checked and found CORRECT (coverage)

Server / storage:
- **Exact part re-upload is idempotent**: a stored part with matching size (+ checksum when supplied) returns `Existing: true` → HTTP 200 instead of 201 (`internal/transfer/upload.go:116-122`, `internal/uploads/service.go:265-270`); the SQL upsert refuses to touch `state='stored'` (`db/queries/uploads.sql:108-121`).
- **Failure paths are detached from request cancellation**: `failPart` and `StorePart` use `partCleanupContext` = `context.WithoutCancel` + 5 s (`internal/transfer/upload.go:233-234,253-256,303-305`), so a client abort still leaves a consistent DB state; covered by `TestFailPartDetachesCleanupFromCanceledRequest` and `TestUploadPartFinalizesPublishedMessageAfterRequestCancellation`.
- **Client disconnect does stop server-side work**: the request context flows into `uploadCtx` → `exactReader` (checks `ctx.Err()` per Read) → the gotd uploader's cancellable group (`internal/transfer/upload.go:146-194,372-391`).
- **Lease renewal is correct and generous**: renew every 20 s against a 60 s TTL, and a renewal failure cancels the in-flight upload and fails the part (`internal/transfer/upload.go:268-301`, `internal/uploads/service.go:27,311-328`).
- **Crash recovery works**: a part left `uploading` by a dead process becomes reclaimable once `lease_expires_at` passes (`db/queries/uploads.sql:118-121`), and `MarkUploadPartFailed` clears the lease so an immediate retry can claim it.
- **`Complete` cannot strand a session**: `completing` → file insert → part copy → `completed` are one transaction (`internal/uploads/service.go:396-521`); `MarkUploadCompleting` requires `state='open'` and errors on 0 rows (`db/queries/uploads.sql:187-194`); a `completed` session returns the existing file (`service.go:413-423`).
- **Concurrent completion is safe**: `LockUploadSessionForCompletion … FOR UPDATE` (`db/queries/uploads.sql:180-185`).
- **`expiresAt` is enforced** on claim and complete (`internal/uploads/service.go:245-247,427-429`) and by the sweep (`db/queries/uploads.sql:307-320`), scheduled `@every 12h` with `MaxAttempts: 3` (`internal/jobs/runtime.go:34,141,181-194`).
- **Cleanup cannot purge parts a live upload needs**: both the listing and the delete join `upload_sessions` and require `aborted`/`expired` (`db/queries/uploads.sql:322-350`); the delete also matches `message_id` to avoid deleting a re-published part, and the worker loops until both expiry and cleanup return empty (`internal/jobs/cleanup.go:74-94`).
- **No whole-file buffering anywhere on the server**: the upload body is streamed by ogen (`internal/api/gen/oas_request_decoders_gen.go:1643` passes `r.Body` for `application/octet-stream`; only JSON bodies are read into memory), `contentcrypto` is a 64 KiB-block streaming reader (`internal/contentcrypto/cipher.go:206-249`), `treehash` keeps one 16 MiB block buffer (`internal/treehash/hash.go:11,32`), and gotd reads 512 KiB chunks with `threads` in flight (`gotd.go:23-33`, `uploader/big.go:48-128`). Per-part RAM ≈ 16 MiB + a few hundred KiB.
- **Body length is verified both ways** (short *and* long) before the part is accepted (`internal/transfer/upload.go:362-406`), with compensating deletes on mismatch.
- **`listStoredParts`'s `limit=200` is legal** (API max is 500, `typespec/common.tsp:64-72`).
- **`/api` requests still get session renewal**: chi's `StripPrefix("/api", …)` (`internal/app/webui.go:210`) rewrites the path *before* `sessionRenewalMiddleware` inspects `/v1/…` (`internal/app/browser_security.go:88-96`), so the 15-minute access cookie is renewed on upload requests too. The UI's XHR `/api/v1/...` path matches `apiFetch`'s base URL (`ui/src/api/client.ts:6`, `store.ts:333`).
- **CSRF does not block the XHR PUT** (same-origin `Sec-Fetch-Site`/`Origin` is accepted, `internal/app/browser_security.go:227-290`).
- **Transport-level retries do have an interval** (gotd's RPC engine uses `RetryInterval`, configured to 2 s at `internal/telegramstore/factory.go:192`); the missing backoff is specific to the custom RPC-error middleware (C3).

UI:
- The **server remains authoritative for part state**: `listStoredParts` re-reads stored parts on every run and skips them (`store.ts:415-425`), so a Resume inside the same tab does resume correctly (as long as the session is still `open`).
- `uploadPart` removes its abort listener on every terminal event and handles an already-aborted signal (`store.ts:338-371`) — no leak of listeners or late-resolution.
- The XHR carries the same cookie auth as `apiFetch` (same origin, no custom headers required).
